# 有争夺风险的新树与空载采集员协防

参加评测的是在冻结 v5 的根搜索里加入联合走法的单文件候选。v5 原本选定的行动继续作为首选比较项。在原有计算预算内，搜索宽度至少为 3 时，预留最多两个名额供下列备选参与原价值函数、对手预测与短程模拟的筛选。

- 己方种植员当前站在空地上，敌种植员在两步之内，且按当步招募后资金能够种树时，可以改走一个离敌种植员更远的邻格。优先考虑周围碳量、合法落点和敌采集员一步可达格。
- 种植员留在可种地，并由一名低于 1 载碳的采集员占住相邻格。敌种植员威胁到树龄最多 6 的己方树时，也尝试让该采集员去争夺路径上拦截。保留已固定回程工人的指令、招募落点以及其他友军的预定位置。余下少于 18 步时沿用原候选生成方式。

[线上回放研究](../analysis/yan-v2-economy.md)给出了本轮假设的来源。实验沿用 v5 的网络、树木收益估值和整步时间预算。

在能取得完整回放的四场 yan-v2 败局中，51 棵新树在 18 步内首次被夺。种树前一帧已有敌种植员在两步内的只有 13 棵。另有 31 棵直到种下以后、树龄仍不超过 6 时才出现这样的威胁，还有 7 棵直到更晚才出现。因此候选在种下之后仍逐步检查协防机会。这是事后按早期易主筛出的树，敌人靠近并不等于护卫一定值得派出。

## 复现

在仓库根目录运行以下命令。对照组固定为 v5-tree-value。输出路径须为新文件。

```sh
git show v5-tree-value:submission.py > /tmp/yan-v2-tree-control.py
python experiments/tree_guard_search.py --base /tmp/yan-v2-tree-control.py --output /tmp/tree-guard.py
CARBON_DEBUG=1 python experiments/tree_guard_check.py /tmp/tree-guard.py --trace-search
CARBON_DEBUG=1 python arena.py --strategies tree-guard=/tmp/tree-guard.py yan-v2=/tmp/yan-v2-tree-control.py \
    --seeds 35831 41893 47269 --jobs 2 --output /tmp/tree-guard-series.jsonl
```

树木威胁时机可用同一检查脚本的 `--loss-replays /path/to/replays` 复算。该目录来自[冻结的完整回放](https://github.com/JUZI1/carbon-league-replays/tree/862bf803e0e07930dfb7fa9ef51ef627a33780d9/replays)，脚本输出纳入的对局 ID 与每局计数。

导出文件 SHA-256 为 `9b4fe64e37e5158b1cc04e09972cb54d5613740f8678eb57dac3d257a158f15f`。在仓库发布的四场 Apollo 回放里，使用各自的部分可见碳图重建估计，拿实际行动作为初始走法，并额外冻结部分工人动作检验约束。双方共 2392 个决策场景中，581 个产生了与原动作不同的备选，包含 483 个改点与 184 个协防备选，其中 49 个确实同时改变了两名工人的动作。逐项检查了指令合法性、固定工人原动作、招募落点和友军落点。对第一场回放的 0 号位重跑第 51 到 198 步间每三步一次的实际搜索，50 次中有 18 次把至少一个新增走法列入根节点，选中 1 次改种位置。搜索根据机器耗时调整宽度，复跑时选择数会波动。
